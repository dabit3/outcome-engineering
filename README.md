# Principles of Outcome Engineering

*Outcome as the new unit of work*. We as humans provide a statement of what should remain true at the end. “Build this Android app” [goal], “Build an Android version of our iOS app and keep it at parity forever” [outcome].

*An outcome carries its own proof*. A good outcome says how the system will know it is true. “Fix the bug from this support ticket” [task], “every support ticket caused by a bug ends in a shipped fix and a reply to the customer” [a target the system can measure itself against]. How well we define the outcome sets the ceiling on what the system can deliver and is the important work we still do by hand.

*Machinery should be invisible*. Skills, Loops, /goal, automations, verification, memory, context, plugins, connectors, and subagents all matter, but almost none of it should be our responsibility. We should bring an outcome, the system should manage / abstract away everything else. Like compiled code we can read what's underneath but rarely need to.

*Human attention is for decisions*. People should step in only for judgment calls a human should make. The system should be smart enough to surface these and notify us when an answer is needed.

*“Done” is a state*. The system should be responsible for the work for as long as we depend on the outcome. It watches the world for changes and proactively keeps the outcome true while looking for ways to make it better (without requiring anyone to ask). The outcome is the durable asset; the code beneath it can be rewritten as many times as it takes.

*Ambition is unbound*. The most challenging part of a big idea was never starting it, it was finishing it and maintaining it forever. Now that our systems can do both we can be more ambitious.

*Authority is bound*. A system that works perpetually and proactively needs a clear limit on what it may touch. We state what the system is allowed to do alongside what we want, and that boundary is what lets us step away.

*Experimentation as a first principle*. Every open question becomes something we can just test. A wrong guess is no longer an opportunity cost because the system can be wrong N times on the way to being right (and in parallel).

Outcome engineering is where we fully give in to our imagination, embrace ambition, and forget that the underlying system and machinery exist.

This way of building is now becoming possible due to the emergence of proactive, perpetual, self-verifying systems. Outcome engineering is already being embraced by some of the best engineers I know and I think will redefine software engineering going into 2027.
